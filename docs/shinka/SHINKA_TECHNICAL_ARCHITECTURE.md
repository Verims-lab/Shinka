## Active Test execution architecture — 015

Browser → existing Base44 function names → verified native `auth.me()` and current User existence → SQL application/owner locks → PostgreSQL product state. `applicationSession` returns the SQL application role used by both Profile/You and AdminGate; `applicationAdmin` is a closed grant/revoke route. No SQL URL/key/driver is shipped in the frontend. Base44 remains identity/OAuth plus redacted internal Health artifact storage only.

`base44/shared/postgres/` separates connection/HTTP, authorization/session, store, receipts, onboarding, Calendar, roles, reset, delete stages and Health metadata. `001_test_authority.sql` contains native constraints and tenant RLS. Every request has an app-bound TEST configuration and explicit synthetic-principal allowlist. Missing configuration fails closed. A shared application row lock protects stable roster/reference inputs; exclusive roster/import/delete admission takes the same row exclusively. Sorted actor/target owner locks serialize related data reads, calculation, writes and receipts in one SQL transaction. This correctness lock order is a deliberate small-Test throughput tradeoff.

Postgres.js 3.4.9 uses one connection per active warm-worker configuration, `prepare:false`, `max_pipeline:1`, transaction-local GUCs and verified TLS for hosted connections. Runtime role is not superuser/owner/BYPASSRLS. Local tests use an isolated loopback PostgreSQL 17.11 cluster. Base44 Deno + Supabase transaction pooler execution is not yet measured. No distributed guarantee is inferred from a worker-local mutex.

Daily creation locks before reading selection inputs and has UNIQUE(app_id,user_id,shinka_date), append-only DB enforcement and readback before commit/return. Calendar actual records + grant/event + receipt commit together; phases/predictions are recalculated from that locked revision, not separately persisted caches. Reset normal writes + stage + receipt commit together. User deletion is a durable SQL-fenced saga around the external Base44 User deletion: no cross-store rollback claim. See [015 report](reports/SHINKA_POSTGRESQL_TEST_015.md) for failure and rollout details. Historical Base44 persistence sections below remain provenance only for the prior deployments.

- `scripts/staticEvidence.mjs` reads repository files only during Vite build/dev on the host. The virtual module exports safe findings, counts, paths and SHA-256 hashes. Raw source and canonical document bodies are not imported with `?raw` or shipped as a source/document registry. H01/H02/H03/H04/H13 declare build-time inspection, not live server inspection.

Report readback selects the URI from the stored record and issues a 300-second signed link. Synthetic tests prove repository behavior; deployed RLS/functions/private-file enforcement requires live two-user verification.
- The CLI builds an isolated temporary harness using actual internal/auth components and canonical tests. Only its test configuration substitutes the SDK; network requests outside loopback are blocked. This is not the Base44 deployment or an authenticated live session.

## Authentication/onboarding architecture

`src/pages/Onboarding.jsx` coordinates existing AuthContext hydration, preferences initialization and state presentation. `onboardingRoute.js` is the canonical eight-state resolver; private backend state is authoritative. `OnboardingScreen` uses shared primitives, centralized copy and bounded services. `authService.beginProviderAuth` checks an explicit true 18+ flag before any provider call; provider initiation is not successful authentication. AuthContext still hydrates the canonical Base44 user.

The `onboarding` backend entry creates a request-scoped SDK client, uses shared authenticated ownership guards and a closed action/field allowlist. Hydration uses owner-filtered queries, singleton duplicate detection and normalized projections. `onboardingValidation.js` shares date-only, age, time, name and cycle validation with UX; server date is calculated from server clock in persisted IANA timezone. The backend revalidates DOB even when client validation is bypassed.

GeoNames uses the server-owned `https://secure.geonames.org/searchJSON` and `/getJSON` endpoints. The onboarding default handler reads `secrets.get('GEONAMES_USERNAME')` from `base44:runtime` inside each request. It no longer captures `Deno.env.get()` at module load. This follows the [current Base44 runtime contract](https://docs.base44.com/developers/backend/resources/backend-functions/overview#read-secrets); a configured secret and a reachable provider are separate facts. The runtime value is trimmed, and missing/blank values fail explicitly before outbound fetch. No Node/Vite environment or credential fallback is used.

`BirthplacePicker` calls onboardingRequest with listPlaceCountries, listPlaceRegions and listPlaceSettlements. The existing production SDK sends JSON POST `/api/apps/<app-id>/functions/onboarding`; these closed actions run after authentication/owner/state checks and before any save/commit. They read only the owner profile (including ACTIVE/duplicate-owner guards) and provider lists; preferences are read only for actions that need them. Legacy searchPlaces remains available for compatibility and regression, but ON-04 never invokes it. Only explicit saveProfile sends the numeric final place ID for independent getJSON resolution and persistence.

Legacy search requests (not selection lists) normalize/encode 2–80-character queries, limit results to 8, select lang en/tr, style FULL and featureClass P, and set the username server-side. An 8-second deadline covers fetch, body read and unused-body cleanup, aborts the fetch and rejects even a stalled transport. The shared request path uses redirect:manual and rejects all 300–399 statuses and opaqueredirect responses before body parsing. It never reads/follows Location or falls back to follow/default. Redirect rejection uses the existing GEONAMES_UNAVAILABLE/502 boundary with GEONAMES_HTTP_ERROR, RESPONSE_VALIDATION and REDIRECT_REJECTION; an opaque status projects to null. Unread unlocked bodies are cancelled on rejection and late responses are discarded unread. Cancellation errors are consumed without replacing the primary failure; stalled cleanup remains deadline-bounded. A non-compliant transport that ignores abort cannot be claimed physically cancelled. Response JSON is bounded to 100,000 UTF-8 bytes and projected to five approved birthplace fields. Editing/clearing invalidates selection and stale results; empty save clears all five fields. No credential, raw query/history, arbitrary provider payload or geolocation reaches persistent product data.

`geonamesDiagnostics.js` separates missing secret, deadline, network failure, HTTP failure, provider rejection and invalid response. The public error_code remains GEONAMES_UNAVAILABLE, with only an allowlisted diagnostic code, numeric HTTP/provider status and provider class. Provider JSON status is examined even on non-2xx HTTP. Code 10 is AUTHORIZATION, 18/19/20 QUOTA, and service statuses stay distinguishable; no raw message is forwarded. Successful empty arrays and successful search status 15 return `{places:[]}`, while status 15 for a selected-ID lookup is rejected. Frontend copy remains the approved generic retry/empty state. [GeoNames status reference](https://www.geonames.org/export/webservice-exception.html). The user reports Preview searchPlaces HTTP 200 with eight places. New list actions, resolve/save and readback remain pending hosted verification; synthetic tests cannot close H10-004.

The fetch-failure continuation adds only `failure_stage` and `transport_class` to this existing diagnostic. Stages are CONFIGURATION, FETCH, RESPONSE_BODY, RESPONSE_VALIDATION or UNKNOWN. A network exception is classified as DNS, TLS_CERTIFICATE, CONNECTION, REDIRECT_REJECTION, INVOCATION_INPUT, TIMEOUT or UNKNOWN from explicit allowlisted runtime codes/names or narrowly recognized Deno/Undici messages. Non-transport failures use null, except explicit manual redirect rejection uses REDIRECT_REJECTION. At most four error/cause nodes are inspected transiently; ambiguous/conflicting evidence stays UNKNOWN. Generic TypeError is not a DNS/TLS diagnosis. An adapter deadline retains GEONAMES_REQUEST_TIMEOUT/504; a runtime timeout before that deadline retains GEONAMES_NETWORK_ERROR/503 with transport_class TIMEOUT. No exception fields are exported. URL-object input, detached fetch call and HTTPS host are retained. The subsequent redirect-policy continuation changes only the redirect option to manual with explicit rejection and cleanup. Generic TypeError remains UNKNOWN; the observed compatibility association is not proof of runtime identity or deployed product success.

For the reported FETCH/UNKNOWN result, the existing admin-only `internalHealth` function exposes a temporary manual action `geoNamesTransportProbe`. It reuses handleInternalRequest/requireInternalAdmin and reads the runtime secret only after authorization and strict payload validation. No new endpoint, auth system or UI action is added. The probe runs in that function's hosted app/deployment context; it is a separate invocation/bundle from onboarding, not evidence that the onboarding invocation itself succeeded. Normal onboarding and automated Full Health never invoke it.

The current probe version is geonames-redirect-policy-v2. It uses four sequential credentialed samples ERROR_1 / MANUAL_1 / ERROR_2 / MANUAL_2 on the same fixed GeoNames search URL, server-owned query and backend secret. One captured detached fetch, URL-object form, parameters and fresh AbortSignal policy are identical; only redirect:error versus redirect:manual changes. It does not adapt on HTTP success, so both pairs run unless a safety limit or cancellation stops the plan. There is no third-party control or credential-free variant in v2. Unlike normal onboarding's 8-second deadline, every diagnostic sample has a uniform 3-second deadline. The existing ceiling of 8 requests / 30 seconds and 250 ms cancellation grace is retained; this plan needs only 4 requests. Unread streams are cancelled and no body/header/Location is inspected. Output remains fixed technical projections, with scope TRANSPORT_ONLY_NOT_PROVIDER_SUCCESS. Even HTTP 200 does not establish provider-authorized search because bodies are not parsed. The user-supplied v1 preview/internalHealth D1/F1 result supports the redirect-policy compatibility hypothesis, pending repeated hosted v2 comparison and normal onboarding verification.

A warm-worker gate rejects concurrent probes and enforces 60 seconds between completed sessions. It is not a distributed rate limit across serverless workers. Unconfirmed abort settlement stops the plan and blocks that worker until the pending operation settles; no background task or automatic retry is scheduled. Removal condition: after hosted normal search, selection and save succeed and any proven fix is recorded, remove this temporary action and entry wiring. Manual use/interpretation is specified in Development Notes.

`base44OnboardingAdapter.js` is the production persistence path. It reuses branded authentication, owner, ACTIVE and protected-record grants from 007. The installed `@base44/sdk` 0.8.54 `entities.types.d.ts` and `entities.js` expose `upsert(records, { key })`, `updateMany(query, { $set })` and filtered reads. Singleton inserts use `user_id`; existing profile/preferences updates include owner/id/native updated-date predicates, and profile updates also require ACTIVE. Explicit NULLs clear the complete optional birthplace group. Create relies on the schema ACTIVE default; no upsert sends account_status to reactivate an existing row. Every write is followed by owner-filtered, field-by-field readback. Duplicate or mismatched state fails closed. This is the strongest SDK-keyed equivalent implemented here, not a native UNIQUE or transaction guarantee.

The canonical `resolveSunSign(birth_date)` uses the approved fixed tropical table. No time/place/fallback is passed. Profile readiness validates existing domain data, adult DOB and the derived sign; incomplete profiles return to ON-04. Approved profile persistence progresses to ON-05 with `completionReady: false` until an actual daily record exists. Skip writes no health data and reaches the finite First Shinka dependency screen. Reload deterministically inspects persisted profile/preferences/consent/period/daily state; no durable skip marker was invented.

The production consent version is exactly `health-consent-v1.0`; the previous missing-source blocker is resolved. The default production adapter path is tested with this exact version against an isolated SDK transport, separately from retained synthetic missing-source negative tests. It verifies current consent, immutable event payload, optional settings, then writes the period last as completion evidence. The event key contains every approved domain field (owner/type/version/time). Its timestamp is the validated, durable `user_health_consent.granted_at`, generated on the authenticated backend for the initial explicit grant. Native `created_date` is not a consent clock. The former native-clock rewrite and `NATIVE_CONSENT_TIMESTAMP_REQUIRED` branch were removed in the ON-05 correction. Missing/invalid business time fails `CONSENT_TIMESTAMP_INVALID`; no timezone is guessed. Existing valid time is preserved byte-for-byte. No event update/delete API exists; identical keyed event/period writes may still affect native updated timestamps under cross-worker races, requiring live verification.

Partial failures can leave earlier writes durable; errors never claim rollback or final completion. Retry reads and reconciles confirmed state. Cross-instance keyed uniqueness, conditional update enforcement, explicit NULL clearing, native metadata and concurrent account/consent/deletion changes remain live verification obligations. The generic `domainAtomic.commitOwnerAction` transaction/receipt contract is unchanged and remains unavailable in production; its original synthetic tests are retained separately.

## Cascading GeoNames protocol — ON-04

`geonamesHierarchy.js` extends the same adapter/request path. countryInfoJSON supplies the bounded country list. For a selected parent, getJSON validates positive ID, country, featureClass A and ADM1…ADM5; hierarchyJSON verifies country ancestry and compatible administrative codes. Missing required codes/ancestry yields PLACE_HIERARCHY_INCOMPLETE rather than a fabricated location. Filtered searchJSON requests only the next nonempty ADM level, or featureClass P settlements within the chosen country/admin codes. Every returned row is checked against that scope, type and ID. Final getJSON rejects non-P records, including a same-name administrative record.

Official references: [countryInfo/get services](https://www.geonames.org/export/web-services.html), [hierarchy service](https://www.geonames.org/export/place-hierarchy.html), [search filters and limits](https://www.geonames.org/export/geonames-search.html). searchJSON uses server-owned q=country code plus country/adminCode1…5/featureClass/featureCode filters; the country-code query pattern is confirmed by the [GeoNames maintainer](https://forum.geonames.org/gforum/posts/list/607.page). No user text query or caller-chosen endpoint/provider parameters is accepted. No childrenJSON call or undocumented childrenJSON paging is assumed.

Pages contain at most 100 options, using documented startRow offsets 0…5000 (free-service window; at most 5,100 accessible records). Each response includes total, offset, next/previous offsets and a limited flag; a larger total triggers an explicit narrowing notice. There is no eight-result list limit. Returned page length must match the expected total/window; missing totals, short pages and duplicate IDs fail safely. Alphabetical ordering is within each provider page, not promised globally. If the provider has no suitable deeper region and the accessible window is exhausted, the UI cannot expose the remaining records: it reports the limit and permits clearing, never pretends completeness.

Only the chosen scope is loaded; the bounded per-picker cache below avoids repeat reads without downloading a whole-country tree. Missing intermediate ADM levels are skipped to the next nonempty level (up to ADM5). No further regions is an explicit successful state; settlements can still be selected at the current scope. Incomplete parent data, zero settlements and provider failure are distinct states.

Country payload cap: 512 KiB / at most 300 country rows. List-page cap: 1 MiB / at most 100 rows. Parent/hierarchy/legacy search/resolve retain 100,000-byte caps. New larger envelopes use bounded streaming reads. Each list action has a monotonic 20-second aggregate budget, per-provider request at most 8 seconds, client list deadline 30 seconds. Manual redirects, pre-parse 3xx/opaque rejection, abort, late-response disposal and unused-body cleanup all remain shared. No retry loop or new transport path is introduced.

`birthplaceSelection.js` owns transient country/path/resources, one generation plus per-resource tickets, and explicit user-triggered loads/retries. Parent changes, Clear and dispose invalidate pending responses; language changes reload the current path under a new generation. Selected saved data is preserved without rebuilding hierarchy. React renders through BirthplacePicker/ShinkaSelect; it stores no path in entities. Client partial-path validation supplements the unchanged server resolve → normalize → five-field persist/readback boundary.

## ON-05 corrective persistence responsibilities

`onboardingCyclePersistence` owns preflight/reconciliation; `onboardingConsent` validates the existing UTC business grant using domainValidation and derives its event. `base44OnboardingAdapter` remains the single SDK/owner/protected-mutation boundary. New consent and settings use insert-only create, so a competing write cannot overwrite an existing grant time or silently edit settings. Event/period retain their full immutable natural keys. The bounded owner read detects more than one row and refuses ambiguity. All existing event history is examined (at most two rows), rather than filtering away a contradictory timestamp. Onboarding is not a regrant/history-editing workflow.

`onboardingCycleGate` coalesces identical pending requests for an owner in one warm worker; different payloads fail ACTION_CONFLICT. It holds at most 256 pending entries, releases on success/error, stores nothing durably, and does not time out/release a still-running write. It is explicitly not a distributed lock. Other workers can race between read/create: duplicate current-consent rows then fail closed without overwriting either time. There is no native unique constraint, cross-record transaction, rollback or proven cross-instance serializability. The independent-worker regression demonstrates this limitation instead of claiming convergence.

Preflight rejects conflicting consent/event/settings/period before mutations. Each subsequent health write rechecks ACTIVE, no open deletion job and the same GRANTED consent id/version/time with withdrawn_at NULL. The final success re-verifies event, settings (including absence), period and consent. Hydration verifies a matching event and valid settings/period before accepting persisted cycle completion; a period without its event returns to ON-05 for recovery. Skip retains its explicit no-write, session-only transition. No new entity, field, receipt, automatic retry or repair endpoint was added.

## First Shinka / Home responsibilities — Buildmarker-011

`dailyCycle` implements the approved current-day phase lookup and last-three observed intervals (single outlier exclusion, half-up mean). No real start → UNKNOWN; NULL settings use 28/5 in computation only. It does not write Calendar predictions/phase caches. `moonIntervals` generates and validates Astronomy Engine 2.1.19 UTC intervals, NEW/WAXING/FULL/WANING, [start,end), contiguous and ordered. The admin Moon importer prepares at least two future years with a stable next-month horizon and exact event timestamps. DM09 compares the first January 2026 full moon with the USNO 10:03 UT reference within a declared 120-second sample tolerance; this is not universal astronomical certification. Rolling automatic renewal is not scheduled in this scope; gaps/expired coverage fail, and the controlled admin mechanism can extend it.

`dailyMessageOperation` derives owner from auth.me(), validates ACTIVE/profile/preferences, computes the day from backend time plus validated device IANA or stored fallback, and returns an existing validated daily row first. It never accepts a client date, owner, category, pair or phase. New generation requires an injected verified durable adapter; the production entry currently supplies none and returns DAILY_ATOMIC_CAPABILITY_REQUIRED before content/health loading. The pure pipeline is implemented and executed with isolated adapters; no hosted first generation is claimed.

For new generation, source-verified content is bounded to this manifest; Moon lookup is bounded to 1,200 rows; at most four latest actual starts yield the last three completed cycles; daily history is at most 40 dates plus one overflow sentinel. No owner cache is introduced and no full-history query exists. Consent/current event and no open deletion job precede health reads; absent/withdrawn consent selects UNKNOWN without reading settings/periods. Malformed grants/events, provider/storage failure or invalid cycles throw explicit errors. Atomic requirements carry the exact health-input grant identity/time/version for the adapter to recheck, alongside owner/account/references. Return rechecks active and consent/deletion state. Calendar writes, scheduler and push remain absent.

`contentImportPlan` owns source-to-schema planning and conflict detection; `base44ContentLibrary` owns bounded SDK reads and full-value insert-or-identical batches; `contentLibraryOperation` owns strict admin dispatch/audit. `dailySelection` owns 40-day selection and snapshots; `domainAtomic.createOnce` remains the sole daily commit/readback protocol. ## Calendar responsibilities and limits — Buildmarker-012

`calendarCalculation` owns strict date/neighbor validation, complete-history phase projection, traceable observation/estimate separation and month projection. It reuses `dailyCycle.cycleEstimate`/`cyclePhaseAtDay`; no engine runs inside JSX. `calendarState` owns guarded pure replacement and commit verification. `base44CalendarReader` is read-only, bounded and owner-scoped. `calendarOperation` authenticates and dispatches closed read/add/edit/delete actions; `domainAtomic.commitCalendarAction` owns the unavailable durable transaction boundary. Production `calendar/entry.ts` passes no adapter and cannot execute mutations. No SDK write tripwire allowance is added.

`calendarService` uses the existing SDK with a 20-second deadline, strict response shape and safe errors. `calendarController` separates selected date, editing ID, confirmation, in-flight action receipt and confirmed data; the hook handles disposal/privacy invalidation. Retry reuses the same action ID/payload/revision; an expired revision requires refresh. Requests are not claimed canceled. Calendar stays lazy behind the existing auth/onboarding resolver; shared `ProductNavigation` enables Home/Calendar and leaves Pattern inactive. Locale-only query values select display language, not authority.

Owner data is memory-only, no persistent browser cache. Every month read fetches bounded complete observations, never one request per day. Two passes detect changing observations/access, with explicit conflict instead of mixed publication; no native snapshot isolation is claimed. Pure recomputation is bounded by 2,500 starts/40,000 days. Unchanged derived rows use indexed reuse rather than quadratic scans. The read response contains only the requested month. Rolling projection refresh is on reads/mutations; autonomous scheduler remains deferred and persisted-cache renewal cannot be claimed while writes are blocked.

The main fast-forward introduced five unreachable generic auth templates; route/import inspection found no application registrations. AuthLayout, Register, ForgotPassword, ResetPassword and OAuthConsent were removed together. Their password/registration surfaces conflicted with the existing Apple/Google contract and reintroduced type errors. Active auth behavior is unchanged.

## Admin Test Tools boundaries — 013

Lazy `TestTools` page → `useTestTools` → one narrow service → `adminTestTools` function. Catalog/copy, preview UI, strict request policy, metadata-only paginated repository, HMAC preview signer, job executor and lifecycle/reset integration have separate modules. No client entity name, role, owner authority or environment override is accepted. SDK 0.8.54 supports the positional filter pagination and service-role User.delete(id) used by the repository. No cascade, token revocation or transaction is inferred.

All seven existing function entries and the new entry wrap the request-scoped SDK with `withUserLifecycle`. Authentication rereads the existing User/role and target operation metadata; absent users or deletion tombstones deny access. This is an early admission check, **not an in-flight write fence**. An active reset overrides onboarding hydration and blocks Calendar; normal profile/cycle validation is reused, with a coordinator-supplied persistence context. Reset step commit and daily completion use a separate transaction port; the sequential onboarding SDK adapter is not that implementation.

`shinka.target-lifecycle/1` requires durable target exclusion shared by every current/future product writer (including notifications/import-triggered work), global admin-roster exclusion, unique operation/receipt keys, persisted start audit, resumable checkpoints and verified final audit. Worker restart must preserve receipts/fences; failed operations keep their fence. The repository has **no production implementation**. The entry always supplies no coordinator: configuring environment/signing secrets cannot unlock it. The in-memory two-worker fixture is only an executable model. See [adapter and rollout contract](reports/SHINKA_ADMIN_TEST_TOOLS.md).


## Production closure investigation — 014

Reviewed SDK 0.8.54 and current official Entity/Actor/CLI documentation. Entity UNIQUE is explicitly unsupported; reviewed APIs do not establish immutable conditional create, CAS publication or a cross-Entity transaction. A single owner aggregate/read-time derived projection reduces Calendar coordination, but without verified conditional replacement still loses concurrent writes. Moving every owner operation into Actor storage would change authority and still requires verified storage/interleaving/retry/roster semantics; it is not enabled on the strength of persistent storage alone.

[Decision 014](reports/SHINKA_PERSISTENCE_DECISION_014.md) specifies the recommended PostgreSQL authority, Base44 identity bridge, distinct Home transaction/Calendar snapshot/Admin saga mechanisms, migration and rollback. It awaits user approval; no new interface is represented as its implementation. Actual entry wiring remains unchanged and all three writers stay independently blocked. Existing onboarding sequential persistence and its known limitations remain visible.

OD-012 is implemented once in `dailyCycle`, consumed by Home and `calendarCalculation`. Window selection precedes filtering. Calendar returns `calculationNotice=CYCLE_ESTIMATE_UNAVAILABLE` separately from technical `calculationError`; its service rejects contradictory notice/predicted-day responses. Missing schema never bypasses lifecycle checks. `prepareSchemaStage.mjs` produces a full hashed schema inventory and a schema-only delta; `base44ReleaseReadiness.ts` is a read-only official-CLI operator script. Neither introduces a product endpoint or starts deployment.
