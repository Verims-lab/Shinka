## Verified source defects and correction

Period persistence and receipt completion are separate ordinary SDK writes. A readback failure can leave the period persisted and its receipt PENDING; no rollback is implied. Raw SDK429 previously retained RATE_LIMITED in diagnostic data but used fallback HTTP500. CALENDAR_READBACK covered several stages and did not reveal which entity read failed.

The previous matching-result shortcut skipped the later rival query, and initial-grant PENDING recovery ran completeCalendarGrant before checking whether grant/event/period were already complete. Resume also looked up the same receipt twice before the first snapshot. The server initial_grant flag can differ from the original health_consent payload when consent was already valid; rebuilding the payload from that flag could reject the saved fingerprint. Resume now verifies the original boolean against the receipt fingerprint, without treating it as consent authority.

The new shared finish path validates fresh two-pass health data, owner/ACTIVE/lifecycle/current Terms/privacy, consent version/event/open deletion, server date, a unique matching period/result, immutable receipt fields and competing operations. Non-grant changes must reproduce base_revision when only the exact intended period change is reversed. Initial-grant completion must match original grant_at, validated current event, one first period and no cycle settings. APPLIED replay requires the saved result revision and matching result. All paths fail closed on conflicting evidence. Readonly status uses the same inverse-revision/result predicate, preventing an impossible continuation based on a matching date alone. The existing initial pending query is owner-wide: known pending work rejects a different new intent before creating an extra receipt, without adding another query. Concurrent not-yet-visible intents still use the retained rival checks.

Complete matching results bypass grant persistence and update only the original receipt. The updateMany predicate contains owner/id/action/fingerprint/base revision/original optional intent fields and PENDING status; readback must verify APPLIED and result_revision. Concurrent cancellation/changed intent is fenced by that predicate and fresh signature checks. Partial grants retain their existing explicit consent/event/cleanup recovery helper. No schema or health-data fields are added, and readonly status never finalizes a receipt.

The redundant first resume lookup is removed. **No confirmedSnapshot confirmation pass is removed or cached.** Admission, normal-write preflight, postwrite readback and final security checks serve different purposes; there was no evidence that removing one would be safe. Recovery of an already complete result avoids the unnecessary grant helper and its repeated guard reads. Added rival/receipt checks are intentionally retained despite their request cost.

## Read retry and diagnostics

Only Calendar installs withCalendarReads below the real lifecycle/Terms/write wrappers. Only filter and raw auth.me reads rejected with actual HTTP429 may retry once per query, at most two additional reads across the request. Wait is at least 500ms, respects Retry-After seconds or explicit GMT date, and is dispatched only within an 18s retry budget with at least 1s reserved. A larger Retry-After is returned rather than shortened. Closed/expired contexts do not dispatch again. This bounds retry dispatch/wait, not an already transmitted SDK request or the total network duration.

SDK create/update/updateMany/delete/deleteMany and encompassing actions are never automatically retried. Post-mutation guard retries retry only the guard GET, not the original write. Calendar response mapping reports HTTP429 and Retry-After when supported by sanitized throttle evidence; genuine authorization errors are not remapped. Other product handlers keep their existing default mapping. A request-local cooldown retains parsed Retry-After metadata if a Terms/lifecycle wrapper replaces the raw exception; it is forwarded only for a verified throttle, never used to remap a denial. The actual native client/Terms test checks a 60-second hint: no internal wait/retry is dispatched and the response preserves the remaining cooldown.

SHINKA_CALENDAR_STAGE, SHINKA_CALENDAR_WRITE, SHINKA_CALENDAR_IO_FAILURE and SHINKA_CALENDAR_READ_RETRY carry a server request UUID, calendar-readback/093 source version, closed stage/entity/method/status, attempts, counts and durations only. No dates, owner IDs, queries, rows, raw messages, headers or credentials are logged. Result verification, receipt verification and response security verification have separate stages. X-Shinka-Calendar-Version identifies the package on success/failure; this tag alone does not verify the complete deployed dependency graph.
