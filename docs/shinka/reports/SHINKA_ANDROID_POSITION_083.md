## Position-only correction

mobile.css keeps the raw root system inset, original painted nav styles and zero dock padding. A navigation-scoped viewport-consumed amount can remove a region the matched viewport already excludes. Effective safe space subtracts the larger of an explicit native declaration and the scoped viewport amount once, never their sum. The whole existing bar moves; no production 48px or 724px offset/height is hardcoded.

ProductNavigation measures current bar/dock bounds and applied bottom before probing the native CSS bottom:0 anchor. The pure navigationInset resolver matches the owner-confirmed behavior only when all these checks agree:

- Android is the platform, the page is top-level and browser display mode is active; zoom scale is 1.
- The available screen is portrait and full-width for the actual client viewport; all required numeric bounds are valid.
- Native CSS, client and usable visible viewport bottoms agree, with no visible bottom occlusion at initial classification.
- The available-screen exclusion equals one whole reported safe inset, and the same inset is independently present in the applied CSS bottom and both painted/dock positions. Dock padding must be zero and bar/dock bottoms must agree.

Android identity and safeBottom alone cannot activate the correction. The rule is an **App-specific viewport compatibility rule calibrated to the owner-confirmed case**, not a universal native-window ownership API. It has no device-size allowlist or fixed pixel subtraction. [Chrome's edge-to-edge guidance](https://developer.chrome.com/docs/css-ui/edge-to-edge) distinguishes clamped and genuinely overlapping viewports. [Screen.availHeight](https://developer.mozilla.org/en-US/docs/Web/API/Screen/availHeight) is available screen geometry, not native WebView bounds; the screen difference alone is insufficient and is not used alone here.

Explicit positive native-consumption declarations retain priority. A matched profile lives only in the existing App-scoped geometry registry, allowing Home/Calendar/Pattern and a reduced keyboard/toolbar viewport to share the same inset ownership. It is invalidated by changed screen dimensions, client width, DPR or inset, non-browser/zoom modes, or a native CSS anchor larger than the matched boundary. Moving into genuine edge-to-edge geometry immediately restores normal safe protection. Missing metrics and unmatched configurations preserve the prior safe-area fallback. Standalone navigation outside the App provider has a mount-local resolver.

Normal-text row height remains **67px**, with the unchanged border, balanced **12px** internal padding, icon/text dimensions, gap, horizontal spacing, colors, focus indicators, links and reselect behavior. Enlarged text can still grow the row. Content reservation continues using the measured bar and actual viewport clearance; existing transform guards keep it fixed through route motion. No authentication, onboarding, Calendar/Pattern calculation, localization, background or data logic changes.

The opt-in diagnostic retains direct mounted references and its fixed privacy whitelist. It additionally reports viewportConsumedBottom and insetPolicy, separately from nativeConsumedBottomDeclaration. For the recorded case, the scoped amount is 48 and the policy is ANDROID_CLAMPED_VIEWPORT, while the original raw safeBottom remains 48.
