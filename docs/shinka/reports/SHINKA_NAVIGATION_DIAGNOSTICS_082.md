## Physical 48px gap: facts, inference and blocker

The owner reports approximately 48 CSS px of empty space below the bar. The screenshots confirm a reported 48px CSS safe inset, no consumed-inset declaration and unavailable navigation bounds. A zero declaration means the web received no declaration; it is not evidence that native consumed zero. With no declared consumption and no visual occlusion, 081's CSS intentionally positions navigation 48px above the visible viewport boundary to protect a genuine reported system overlap.

The extra band shown above a separate Android system navigation area is consistent with duplicated consumption. That is an **inference**, not measured native ownership. The screenshots omit the upper viewport/build fields and all bar/dock bounds are null. Screen availWidth/availHeight alone do not establish the WebView's window position or which edge native UI already consumes. [Screen.availHeight](https://developer.mozilla.org/en-US/docs/Web/API/Screen/availHeight) describes available screen space, not the native WebView rectangle. [Android inset guidance](https://developer.android.com/develop/ui/views/layout/webapps/understand-window-insets) distinguishes actual overlap and requires handled native inset types to be zeroed before forwarding them.

There is no native wrapper/inset bridge implementation in this repository, and no physical debugging connection is available. Missing viewport.innerHeight, viewport.clientHeight, visual.height/offsetTop, screen.height and build fields were requested while the independent diagnostic correction proceeded. Correct bar/dock bounds and native window bounds are still required to verify ownership. It is unsafe to identify all Android 48px insets as consumed or infer consumption from a screen-size coincidence. Genuine iOS and other Android overlap protection remains intact.

The 48px regression supplies host ownership explicitly: when all 48px are already consumed, the existing contract places the entire painted bar at the usable viewport boundary with zero additional gap; when 48px genuinely overlap the web viewport, all 48px remain protected outside the unchanged bar. That is a **synthetic host model**, not a newly observed native declaration or an automatic fix for the pictured phone.

**Physical incident: USER_REPORTED_FAIL (about 48px) on the supplied build; 082 physical after-measurement: NOT_RUN / PENDING.** Navigation positioning closure remains OPEN_PENDING_DEVICE_GEOMETRY_AND_NATIVE_OWNERSHIP. This package corrects the diagnostic defect needed to obtain those measurements; it does not claim the Android gap is fixed. Once measured, the preferred native correction is zeroing the inset already handled by the host; alternatively the host can provide the existing dynamically measured CSS-pixel consumption declaration. That host code is outside this checkout. No native configuration was invented or changed.
