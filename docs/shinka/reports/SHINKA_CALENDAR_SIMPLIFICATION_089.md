## Approved interaction and verified data meanings

The current owner request replaces 062's global Edit dates / Save editing mode. CalendarDayDetails and calendarSelection replace CalendarEditor and calendarDraft. A tap inspects the date below the grid without a write. A recorded start shows “Regl başlangıcı kaydedilmiş”, Change date and Delete record. An eligible past/today empty day offers Save as period start. Moving is an explicit source-record intent, followed by a new day and Save date change; the original native period ID is retained. Cancel writes nothing. Deletion keeps the existing named-date modal, Escape/Back and focus restoration. Today/future dates remain inspectable, with no future save. The backend still rejects future add/edit independently.

Verified directly in calendarCalculation/calendarOperation/calendarService:

- `starts` contains actual IDs/start dates **only in the requested month**, not the complete history. UI spacing checks are a convenience over that snapshot; the backend still validates both neighbours using full history and the existing 15-day rule.
- `recordedDays` expands actual starts by configured/default period duration (validated 1–10 days, default 5). These are derived display intervals, not separately saved observations of bleeding on each date. Starts from the previous month can produce recordedDays with no corresponding start in this month.
- `predictedDays` contains PREDICTED/MENSTRUAL phase dates, excluding actual intervals. A month's first predicted day may be the middle of an estimated interval; it is never labelled as a predicted start. A past predicted day can still be offered as an actual start, subject to existing validation.

The two-key legend identifies recorded starts (filled dot) and predicted periods (soft dashed tint). Derived recorded intervals keep their soft tint; today stays bold/underlined and selection uses a separate ring. Unsaved selection no longer receives the prediction fill or a saved marker. Context explains the remaining states. Normal inspection clears on month changes rather than applying the wrong month's projection; explicit move drafts retain ID/target through month/year/tab navigation in memory. No health field, end date, duration input, batch, browser storage or new backend operation is added.

Month/weekday text may wrap at enlarged sizes. On narrow dark screens, the grid's existing negative gutter margins can place enlarged glyphs outside the shared reading surface. A Calendar-only extension of the existing dark reading color protects them; original artwork, logo, global palette, profile 087, navigation 083 and Home 088 are preserved. The shared test measurement now evaluates actual non-space text ranges rather than transparent control padding. No AA threshold is relaxed.

## Bottom warning investigation and bounded fix

The reported warning/Check status is produced by `outcome === 'unknown'` after a write/confirmation failure, or by a server-projected pending receipt on reopening. This is legitimate when a write may have happened. `checkedAction: APPLIED` already cleared error/retry/continuation after matching original action/operation/revision/period/date and the existing mutation readback check; this behavior is preserved. Merely seeing a period row never substitutes for a confirmed receipt.

RC11 reproduces a verified client defect before the fix: a definite PERIOD_CONFLICT rejection followed by a verified ABSENT receipt set canContinue, causing the old UI to show misleading unconfirmed-change guidance. The controller now retires that rejected attempt only after ABSENT is verified without another pending review. A genuine unknown plus ABSENT/PENDING still remains unresolved. RC12 protects cleanup after an explicit conflicting receipt: no continuation and no false success. Expanded RC08 requires failed/mismatched/competing status reads to retain an original unknown lock, preventing a replacement write. Only a positively checked receipt or a privacy boundary can retire that uncertainty.

Read-only Check remains read-only, repeated checks coalesce, and explicit continuation rereads and reuses the original action ID/revision/payload within the existing budget. Native owner/ACTIVE/lifecycle, consent/grant timestamps, full-history date validation, receipts, calculation and service contracts are unchanged. Technical recovery controls appear only for actual uncertain/pending/conflicting operations or read failures; ordinary field validation does not offer a misleading status/continue action. Confirmed success retains the inspected date and clears recovery UI.

The supplied warning text alone does **not** establish the cause of a particular live Base44 instance. It could represent a genuine pending/native/transport/readback failure or another deployed build. Actual deployed build and safe original error/action/receipt evidence are still required for that instance; no live receipt was inspected/reset or user write repeated here.
