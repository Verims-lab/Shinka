## Position-only change and ownership contract

The dock has zero bottom padding and the same border-box bottom as the visible bar. The whole bar is positioned above the remaining unconsumed system boundary; genuine safe space is outside the bar, not an additional dock row. Flow reservation is measured bar height plus actual clearance to the client viewport. The native CSS-bottom calibration and visual-only viewport correction remain. Inset-size and host-style observation refresh reservation even when only position changes; observers are disconnected on unmount.

The local WebKit resize regression also exposed delayed document metrics: native CSS bottom and visual height were already 800px while clientHeight still reported 480px. The bar was positioned correctly, but the placeholder retained only 67px instead of including the protected inset. A non-rendered fixed probe observes CSS viewport height and unconsumed-inset width separately, ensuring a post-layout measurement even when resize events precede the clientHeight update. It neither changes the navigation row nor receives input.

Normal navigation remains 67px high with the existing border, balanced 12px internal padding, 20px icons, caption metrics, icon/label gap, colors, equal columns, routes and focus behavior. Larger accessibility text can still grow it. Home, Calendar, Pattern and the existing shared You footer use the same component. No authentication, product, localization or background behavior changes.

The browser reports a safe inset, but cannot reveal external native view bounds or whether a wrapper forwarded an already-consumed value. There is no reliable universal Android/user-agent or screen-height test for this distinction. [Android's native guidance](https://developer.android.com/develop/ui/views/layout/webapps/understand-window-insets) requires native-handled inset types to be zeroed before forwarding them; blindly suppressing subsequent notifications can retain stale insets. [Chrome's safe-area guidance](https://developer.chrome.com/docs/css-ui/edge-to-edge) also distinguishes a genuine system overlap and positions bottom controls above that boundary.

Preferred integration: the native host forwards zero for the system space it already consumes. If it intentionally forwards the full value, it can declare its measured consumed amount in the root CSS custom property `--shinka-native-consumed-bottom` in CSS pixels. The web subtracts only that declared amount, clamped at zero. The default declaration is zero, preserving genuine Android and iOS safe areas. This is an **explicit host contract**, not automatic detection or an existing Base44 API.

The host must update the declaration from actual native bounds on inset/window/keyboard changes, converting native dimensions to CSS pixels and clearing consumed amounts when ownership changes. Never hardcode the test's 30px value in production.

**No code in this checkout supplies a native-consumption declaration.** Thus an incorrectly forwarded 30px inset with no host declaration still leaves the protected bar 30px above the web viewport bottom, as under 080. Moving the inset from padding to positioning alone does not solve that host error. Do not claim this package automatically removes the physical Android gap. Closure is **OPEN_PENDING_DEVICE_MEASUREMENTS_AND_NATIVE_OWNERSHIP**. The host must zero consumed insets or provide measured consumption; changing an Android-wide default without those bounds would risk covering genuine system controls.
