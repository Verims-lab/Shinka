## 052 — Calendar and Pattern read recovery (2026-10-30)

Calendar/Pattern tab return, focus, visible and online events share bounded read admission. Offline events pause read attempts until online; logout seals the old controller. No ownership, onam, reset/deletion gate is relaxed.

## 039 — uncertain preferences and access-loss behavior

A You preferences save with a lost/ambiguous reply retains its original section, payload and revision. Edit, cancel, fresh save and load cannot discard that pending outcome; read-only verification failure keeps it unknown. Only verified result or the same explicit retry reconciles it; access denial clears the view. UI and controller enforce the same lock. Reopening the route reads persisted state rather than claiming rollback or durable client-draft persistence.

Home retains a confirmed day on ordinary network/content errors, but clears cards and hydrated name on explicit account/owner/profile/consent/lifecycle denial. Session end prevents further automatic/manual hook requests for that lifetime and drops late results; a fresh authenticated mount can load normally. No daily timestamp/content/onam change. ## 038 — Calendar result and retry semantics

A rejected invalid/future/duplicate/too-close date creates no new receipt/period. Transport failure can mean no write, saved write with lost reply, or partial write: the UI shows unknown and retains the same payload/action ID. Reopen reads a unique pending receipt and reconstructs explicit resume, including add/edit/delete and initial grant. Resume checks current guards, expected state and readback before APPLIED/visible success; pending/error paths never auto-delete/cancel. Saving/resuming a past date selects its month for visible confirmation. A passive read can be superseded by explicit retry, and its late response is ignored. Multiple intents/stale revision remain conflicts with existing records intact; native SDK is not a transaction or distributed lock. Existing OD-012 outlier and future-date protections remain. No reset/new account is required for a recoverable unique intent.

## ON-05 partial-write recovery

An existing valid consent without its event/period is a resumable partial operation. Continue with the same intended inputs keeps the saved consent time and creates only missing matching records after verification. Retry/reload/double tap in one worker does not issue another grant time; confirmed matching rows are not written again. Conflicting settings, period start, version/history or withdrawn consent is refused; onboarding cannot silently become a health editing/regrant flow. All required records must be read back before Continue succeeds. Reload cannot infer cycle completion from period alone when its consent event is absent. Skip writes nothing, including when an earlier failed attempt left consent behind; it neither revokes nor deletes that consent. Live success with the same partial account remains required.

## Historical checkpoint — OD-012 behavior and production closure — 014

Real starts remain ≥15 days apart. Longer than 60 days is not a validation error: keep the exact dates. Determine the last three completed intervals first; use only 15–60 values within that window, without reaching farther back. Existing outlier/average/half-up rules apply to the remaining values. No supported completed sample gives no estimate/current phase; no completed intervals retains initial/28 behavior. Completed >60 intervals have no derived phase rows. Supported historical intervals can retain their historical phases even when no current estimate exists.

A successful Calendar plan replaces all obsolete current predictions/phases and returns a central TR/EN information status, not a failed-save message. The production transaction remains blocked, so this is enabled calculation/reader behavior plus isolated mutation evidence, not a hosted save. New Home generation uses the same rule and UNKNOWN only for unavailable phase; existing daily snapshots remain immutable. Missing consent/deletion/account guards and technical/data errors never become UNKNOWN.

Home → Calendar → reset → delete is the proposed enablement order after the independent prerequisites in the [architecture decision](reports/SHINKA_PERSISTENCE_DECISION_014.md). No feature is declared live-complete in 014.
