## Chosen Base44 primitives

Installed SDK **0.8.54** was compared with [entity methods](https://docs.base44.com/developers/references/sdk/docs/type-aliases/entities) and [entity schemas](https://docs.base44.com/developers/backend/resources/entities/entity-schemas), checked 2026-10-20. `create` inserts; `update` merges; `upsert` merges matching keys and can overwrite existing snapshots. `updateMany(query, data)` returns `success`, `updated`, `has_more`; `deleteMany` returns `success`, `deleted`. Filtered update with exact previous value and count/readback narrows and detects conflicts; **it is not documented linearizable compare-and-swap**. Native UNIQUE is unsupported. No Entity multi-collection transaction, rollback, lock, visibility bound or distributed uniqueness is claimed.

[Actors](https://docs.base44.com/developers/backend/resources/actors/overview) offer actor lifecycle and persisted key/value state, but process memory resets on idle/restart and does not supply an Entity transaction. Ordinary Entities/functions were selected: fewer authorities and no actor-to-Entity commit bridge. No new generic coordinator, service or worker-local lock is presented as a distributed guarantee.

### Home reconciliation

Every candidate must validate owner, local day, persisted business `generated_at`, pair/category IDs and four immutable text snapshots. Sort by parsed generated_at ascending, then codepoint ID ascending; choose first. Identical or conflicting rows are **retained**. If stored text/category/pair differ, Home shows a localized reconciliation notice. No category re-assignment, history deletion or text overwrite occurs. A late-visible earlier candidate can change the selected snapshot on refresh; with the same observed candidate set the winner is stable. This is the explicit relaxation of one physical row per user/day, not a seed-based promise. A fixed seed would not freeze changed profile/catalog inputs. All candidates, including losers that might have been shown, count in the 40-day exclusion window. Existing fallback chain and day-41 eligibility remain. Bounded pagination rejects >4000 candidate rows rather than using truncated history. Reference readiness failure is independent from persistence capability.

### Calendar receipts and recovery

Backend-only UserCalendarAction stores owner/action ID, canonical intent fingerprint, base/result revision, operation, target period ID, desired/previous dates, initial_grant, persisted grant_at, status and started_at. It contains **health data**, not audit metadata; direct CRUD is false. Same action with different input rejects. New action ID with the same single pending fingerprint resumes that intent after reload. New requests compare the displayed revision. Edit/delete include exact previous date in the filter and require a one-row result; readback verifies the outcome. Losing response after mutation leaves the receipt pending; retry verifies already-saved desired state before advancing it, rather than applying the mutation again.

Initial explicit add+consent persists a grant intent time before current consent/event/period. Subsequent retries reuse this time and verify the matching current grant. Missing event after current consent is recoverable: read returns a limited recovery view, with no predictions/health history presented as complete; the user's Retry sends the owner-scoped receipt ID and resumes. No new consent instant, fabricated grant or auto-grant on selection occurs. A withdrawn grant still requires valid completed deletion, matching withdrawal evidence and no residual health state. Ordinary dates remain YYYY-MM-DD; >60-day actual intervals are preserved under OD-012. No physical UserCyclePrediction/UserCyclePhaseDay writes occur; old caches are ignored, retained until approved cleanup. Receipts must also be removed by future health-withdrawal cleanup (that workflow is not implemented here).

Visible conflicting pending intents suppress predictions and show review instructions. “Keep these dates and clear pending attempts” marks pending receipts CANCELLED after revision check and checks no pending rows remain; it never changes actual dates. Close other clients before confirming: cancellation cannot recall an SDK call already sent. A subsequent read detects pending/invalid actual state; revision detection cannot prove that no undetectable race occurred. Conflicting intents retain previous/desired dates for authorized recovery. Duplicate actual-date rows or invalid spacing remain a hard conflict: an operator reviews owner-scoped receipts and actual IDs with the user under a maintenance window, preserves evidence, and makes only an explicitly approved correction. There is no arbitrary deletion or automatic date clamping.

### Reset continuation

AdminTestOperation gains optional `step_fingerprints` (hashes only). Preparation writes RESET_ACTIVE/PROFILE without changing product rows. Normal onboarding input uses its usual validation and persistence; then verified progress goes PROFILE → CYCLE → FIRST_SHINKA → DONE. If progress fails after a normal write, the input fingerprint and saved record remain; retry with identical input validates it and advances. Different input is rejected while that step is pending. Reset Cycle may confirm matching existing period/settings; it cannot edit historic dates or create a fresh grant over existing history. Use Skip to preserve history, or finish and use Calendar for a date change. Same-day ON-06 reuses the saved daily snapshot. Final audit is verified before terminal progress. No profile/health request bodies are placed in AdminTestOperation.
